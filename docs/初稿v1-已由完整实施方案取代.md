# 飞牛影视「网页版」改造实施方案（借 fndesk 原理）

> 目标：让**浏览器直接打开飞牛影视**（`/v`）就能生效 Fntv-Plus 的增强能力，而不只是在 Electron 客户端里生效。
> 参考对象：`https://github.com/IMGZCQ/fndesk`（已克隆到 `D:\GitHub\Fntv-Plus-Desktop\fndesk` 作为原理参考）。

---

## 一、从 fndesk 扒出来的关键事实（已在其源码中确认）

| 事实 | 路径 / 机制 |
|---|---|
| 飞牛影视 web 根目录 | `/var/apps/trim.media/target/static/` |
| 影视入口 HTML | `/var/apps/trim.media/target/static/index.html` |
| 影视 JS/CSS/图片资源 | `/var/apps/trim.media/target/static/assets/`（hash 文件名） |
| 飞牛桌面/登录页前端 | `/usr/trim/www` |
| fndesk 的系统备份区 | `/usr/trim/share/.restore/`（`www.bak`、`tow/`、`raw/`） |
| fndesk 改影视的手法 | ① 在 `static/index.html` 里插 `<script>`（favicon、标题）② 替换 `assets/` 下 `.webp` 背景图 ③ 扫描 `assets/*.js`、`*.css` 做文本替换（LOGO、透明度） |
| 应用形态 | FPK 包：`manifest` + `cmd/`（生命周期脚本）+ `config/privilege`（**run-as root**）+ `config/resource`（数据共享目录）+ `wizard/`（安装向导）+ `app/ui/`（桌面图标 + CGI）+ `app/server/`（Node 后端） |
| 后端启动 | `cmd/main` 由飞牛系统以 `TRIM_*` 环境变量调用 `start/stop/status`；架构自适应找 node（v24→v22→全局→下载），后台跑 `server.js`（9990 端口），`status` 发现进程挂了自动拉起 |
| 免开端口访问 | `app/ui/config` 定义 `type=iframe, url=/app/fndesk, gatewayPrefix=/app/fndesk` → 飞牛统一网关 → `app/ui/index.cgi`（bash CGI：静态直出 + 反代 127.0.0.1:9990） |
| 分发方式 | 应用中心左下角「手动安装 FPK」，无需官方审核；另提供 `bash <(curl ... restore)` 应急还原脚本 |

**核心结论**：fndesk 没有任何魔法 —— 就是 **root 权限 + 直接改写飞牛 Web 前端的静态文件**。这也正是「网页版生效」的唯一可行路径。

## 二、三条路线对比

| 路线 | 生效范围 | 改动 NAS 系统文件 | 风险 | 说明 |
|---|---|---|---|---|
| A 纯客户端注入 | 仅 Fntv-Plus 内 | 否 | 无 | **现状**：`src/preload/plugins/*` 已实现 |
| B 服务端改写文件 | 浏览器 + 客户端 | **是** | 中 | fndesk 路线：改写 `trim.media/static/index.html` |
| C 混合（B+A） | 浏览器 + 客户端 | 是 | 中 | 一份 payload，两端复用；客户端检测去重 |
| **D 后端反代注入** | 浏览器 + 客户端 | **否** | **低** | **FPK 后端反代 `/v`，在 HTML 响应里注入（见第十一节）** |

> **[2026-09-07 修正] 主推 D**。详见第十一节：既然飞牛影视没有独立端口、挂在系统 Web 端口 `/v` 下，
> FPK 后端完全可以「反代 + 响应注入」，从而**完全不碰系统文件**，消除 B/C 的升级失效、与 fndesk 冲突、白屏等全部风险。
> payload 与 C 完全一致，只是**注入点从「改文件」变成「改响应」**，第十一节的方案对第五~八节仍然适用（只需换注入通道）。

payload 复用是核心诉求：不重复维护两套 UI 逻辑，且老用户没装 FPK 时客户端注入仍能兜底。

## 五、注入机制（幂等 + 可回滚 + 可与 fndesk 共存）

### 5.1 注入块格式

在 `/var/apps/trim.media/target/static/index.html` 的 `</body>` 前插入：

```html
<!-- FNTV_PLUS_INJECT_BEGIN v1.0.0 -->
<script id="fntv-plus-cfg" type="application/json">
{"version":"1.0.0","features":{"embyWall":true,"customLogo":true},"payloadRev":"2026.09.07"}
</script>
<script>
/* fntv-plus.user.js 内容原样内嵌（IIFE，约几十 KB，无外部依赖） */
</script>
<!-- FNTV_PLUS_INJECT_END -->
```

> **为什么内嵌而不是 `<script src="...">`**：外链要依赖网关路由（`/cgi/ThirdParty/...`）且影视页面可能从别的 origin 打开，路径易失效。fndesk 也是内嵌。更新 payload = 整块替换这一段，零路由依赖。

### 5.2 apply 算法（幂等）

```
1. 读 index.html
2. 备份（首次/版本变化时）→ <data>/backup/index.html.<影视版本>.<时间戳>.bak
3. 用正则 /<!-- FNTV_PLUS_INJECT_BEGIN[\s\S]*?FNTV_PLUS_INJECT_END -->/ 移除旧块
4. 在 </body> 前插入新块（若找不到 </body> 则追加到文件尾）
5. 写回，chmod 保持原权限（通常 644）
6. 记录状态到 <data>/state.json：影视版本、payload 版本、注入时间、备份路径
```

**关键点：只做「标记块级别」的增删，绝不整文件替换** —— 这样 fndesk 插的 script、飞牛自己的代码都不受影响，两者可共存。

### 5.3 版本感知

- 影视版本读取优先级：`/var/apps/trim.media/manifest`(version 字段) → `/var/apps/trim.media/VERSION` → 应用中心数据库 → 兜底取 `index.html` 的 md5
- 每次 apply 记录版本；影视升级后版本变化 → 管理后台提示「影视已升级，需重新应用」
- `cmd/main` 起一个低频 watchdog（如每 10 分钟）：检测标记块是否还在，不在则自动重新注入

### 5.4 还原

- 一键还原：用最近的备份覆盖 index.html；无备份则按标记块剥离
- 卸载 `uninstall_callback` 自动还原
- 提供应急脚本（照抄 fndesk）：`bash <(curl -fSL# https://xxx/?url=restore)`

## 六、Fntv-Plus 客户端改造点

### 6.1 远程注入去重（必做）

新增 `src/preload/core/remoteGuard.ts`：

```ts
// 页面加载后判断：NAS 端是否已注入 payload
export function remotePayloadActive(): boolean {
    return !!(window as any).__FNTV_PLUS__;
}
```

`preload/index.ts` 加载插件前检查：若远端已激活，则跳过**同 id** 的本地插件（embyWall / customLogo / glassUI / listLayout / previewThumb …），只保留依赖 Electron IPC 的（danmakuWeb 走代理、playMemory 走本地存储、players 相关）。

### 6.2 插件分层（重构，收益最大）

把 `src/preload/plugins/` 按依赖拆分：

```
src/preload/plugins/
├── web/            # 纯 DOM，零 Electron 依赖 → 可打包成 fntv-plus.user.js
│   ├── embyWall/  customLogo.ts  glassUI.ts  listLayout.ts
│   ├── previewThumb.ts  pageAnim.ts  a11y.ts ...
└── host/           # 依赖 Electron/IPC → 仅客户端运行
    ├── danmakuWeb.ts  playMemory.ts  playChoice.ts ...
```

配套 `src/preload/core/host.ts` 适配层：

```ts
export interface Host {
  storage: { get(k: string): Promise<any>; set(k: string, v: any): Promise<void> };
  request(opts): Promise<any>;      // Electron: IPC → 主进程 axios；浏览器: fetch
  log(...args): void;
  isElectron: boolean;
}
```

两端各注入一个实现，`web/` 插件只依赖 `Host` → 一份代码两端跑。

产物同时用于：① FPK 的 `app/server/payload/` ② 本地 Playwright 回归测试（你已有 headless chromium 环境）。

## 八、风险清单（务必逐条设防）

1. **影视升级会覆盖 index.html** → watchdog 检测标记 + 自动重注入 + 后台提示；fndesk 也面临同样问题（它靠用户手动点「立即生效」）。
2. **与 fndesk 冲突** → 必须只做标记块增删，不整文件替换；实测两者同时安装后的页面。
3. **影视 JS 是 hash 文件名打包产物**，升级后全变 → payload **不要依赖任何具体资源文件名**，只做 DOM / 路由 hook（`location.pathname` + MutationObserver），fndesk 那种扫 `assets/*.js` 做文本替换的方式很脆、不建议学。
4. **改系统文件可能影视白屏** → 先备份再写、写入前校验 HTML 结构、提供一键还原 + 应急 curl 脚本。
5. **浏览器缓存导致"改了没生效"** → 管理页显眼提示 Ctrl+F5 / 无痕模式；payload 内带版本号便于自查（fndesk README 说 99% 不生效都是缓存）。
6. **FPK 需 root 权限** → 明确告知用户，卸载时务必还原。
7. **payload 体积** → 内嵌进 index.html，控制在 100KB 以内；超大资源（图标库）走外链。

cd /var/apps/trim.media/target/static
cp index.html /tmp/index.html.bak

## 十、与 fndesk 的差异化（我们做得更好的地方）

- fndesk 是「配置 → 生成 → 覆盖系统文件」的**文本替换**模式，脆弱且功能受限于能替换什么；
  我们是「**注入一个运行时脚本**」，脚本内部可以做 DOM 改造、路由 hook、远程配置下发，能力上限高一个量级。
- fndesk 与客户端是两套代码；我们**一份 payload 两端复用**。
- fndesk 升级影视后要手动重新生效；我们计划用 **watchdog 自动重注入**。

## 十一、【新增·主推】方案 D：走后端反代注入，零系统文件改动

### 11.1 关键事实

- **飞牛影视没有独立端口**，挂在系统 Web 端口的 `/v` 下（系统默认 HTTP 5666 / HTTPS 5667，来源：`src/main/handlers/plugins/auth.ts` 注释）。
- 因此影视页面与飞牛主站**同源同端口**，这同时意味着：
  - FPK 后端提供的 API 与影视页面**天然同源 → 无 CORS**（第十节的数据源代理方案成立）；
  - 后端可以 `curl http://127.0.0.1:5666/v/...` 回环拿到影视原始响应（root 权限，完全可达）。

### 11.2 链路

```
浏览器 → http://<nas>:5666/cgi/ThirdParty/fntvplus/index.cgi/v/
           │  （飞牛统一网关，免开端口）
           ▼
       index.cgi（bash，静态/转发；可直接抄 fndesk 的）
           │  转发到常驻后端
           ▼
       Node 后端 127.0.0.1:22350（FPK 自带，root 运行）
           │  ①回环请求 http://127.0.0.1:5666/v/... 拿原始响应
           │  ②HTML 响应 → 注入 payload 块后返回
           │  ③非 HTML（js/css/图片/视频流）→ 原样透传
           ▼
       原始影视服务
```

三种落地形态，按优先级：

| 形态 | 访问入口 | 优点 | 缺点 |
|---|---|---|---|
| **D1 CGI + 常驻 Node（推荐）** | `/cgi/ThirdParty/fntvplus/index.cgi/v/` | 免开端口、性能好、fndesk 已验证 | 实现分两层 |
| D2 独立端口 | `http://<nas>:22350/v` | 最简单 | 需开防火墙端口、用户要记端口 |
| D3 纯 CGI | 同 D1 | 零常驻进程 | 每请求 fork bash+curl，性能差 |

### 11.3 注入逻辑（与方案 B 的 payload 完全一致，只换通道）

```js
// Node 后端：反代 + 注入
const r = await fetch('http://127.0.0.1:5666' + req.url, { headers: forwardHeaders });
const ctype = r.headers.get('content-type') || '';
if (!ctype.includes('text/html')) return pipeThrough(r);        // 资源/视频流：透传
let html = await r.text();
html = html.replace('</body>', INJECT_BLOCK + '</body>');       // HTML：注入
res.writeHead(r.status, { ...pickHeaders(r), 'content-length': Buffer.byteLength(html) });
res.end(html);
```

### 11.4 相对方案 B（改系统文件）的收益

| 维度 | B 改文件 | D 反代注入 |
|---|---|---|
| 影视升级后失效 | 会，需 watchdog 重注入 | **不会**（每次反代都是最新版） |
| 与 fndesk 冲突 | 有（同改 index.html） | **无** |
| 白屏风险 | 有（改坏系统文件） | **无**（改坏只影响自己的入口） |
| 卸载残留 | 需还原备份 | **零残留**（删 FPK 即可） |
| 一键还原 | 需备份机制 | **天然可还原**（访问原 `/v` 即是原版） |
| 入口 URL | 不变（`/v`） | **变**（需新入口） |

### 11.5 必须处理的坑

1. **入口变化**（最大代价）：用户得访问新 URL。
   → 解法：FPK 提供一个「影视增强版」桌面图标（照抄 fndesk `app/ui/config` 的 `type=iframe, url=...`），用户点图标即进增强版，点原影视图标仍是原版。**这反而是卖点：原版/增强版可自由切换。**
2. **`<base href>` / 相对路径**：HTML 里若有相对路径，需注入 `<base href="/v/">` 或让 CGI 正确转发任意子路径（D1 天然支持，因为 `/v/...` 子路径也会进我们的 CGI）。
3. **Range 请求（206）**：视频流若经过反代，必须透传 `Range` / `Content-Range` / `Accept-Ranges`。fndesk 的 `index.cgi` 已有完整实现（含 `dd skip/count_bytes` 分片），可直接抄。
4. **WebSocket**：影视若有 WS（实时进度/通知），需 WS 透传（Node 侧用 `http-proxy` 或 `ws` 转发）。
5. **Cookie / 鉴权头**：原样透传（同源，无跨域问题）。
6. **nginx 限制**：fndesk 注释提到网关有 **1MB 上传限制**，大请求需走独立端口（D2）或提示用户。
7. **缓存**：反代响应需设 `Cache-Control: no-store` 或带版本串，否则浏览器缓存旧 HTML 导致 payload 不更新。

### 11.6 与客户端的关系（不变）

客户端 `loadURL(server + '/v')` 改为可配置「增强版入口」；`remoteGuard` 去重逻辑不变。
若用户只想用客户端、不装 FPK，本地 preload 注入仍兜底 —— 三条通道共用同一份 payload。
