## 一、结论先行

| 项 | 结论 |
|---|---|
| **能不能做** | 能。做一个官方 FPK 应用 `fntvplus`，以后端**反代影视页面 + 响应注入**的方式实现 |
| **要不要改影视系统文件** | **不要**。只读 + 响应注入，零系统文件改动 |
| **浏览器直开能生效吗** | 能，但入口 URL 变为 `/app/fntvplus/v/`（用**官方桌面入口**包装，对用户无感） |
| **范围** | 35 项功能：✅16 直接做 / ⚠️10 需改造 / ❌9 做不到（详见功能评估文档；外部播放器「能调起」已纳入 M4，见第七.5 节） |
| **后端语言** | **Go**（不是 Node）—— 理由见 4.4 |
| **合规边界** | FPK 应用本身完全合规；「注入影视页面」属灰色地带，风险见第十节 |
| **目标群体** | **不想在电脑上安装任何客户端、只用浏览器看片的人** |
| **外部播放器** | **只做「fntv:// 单向唤起本机播放器」（能调起即可）；进度回传网页端先搁置**（详见第七.5 节） |
| **明确不做** | 网页端**独立**承载 MPV/PotPlayer（无客户端、无本机常驻服务）—— 物理隔离，见第七、八节 |

### 2.4 开放 API（官方 `api/calling/`）

**后端 API** —— Unix Socket，不走网络端口：

```bash
curl --unix-socket /var/run/trim_open_gateway_apiscope.socket \
  -X POST http://localhost/api/v1/trimapp \
  -H 'Authorization: Bearer $TRIM_API_TOKEN' \
  -d '{"reqId":"1","req":"trim.system.getPlatformConfig","appName":"fntvplus","data":{}}'
```

- `api-scope` 声明在 **`config/resource`** 里（如 `trim.file.userAccess`、`trim.system.getPlatformConfig`）
- `TRIM_API_TOKEN` **每次从环境变量读，不要持久化、不要下发到前端**
- 我们能用到的：读系统语言/版本（做版本兼容提示）、路径转换、文件权限检查

**前端 JS SDK** —— `@trimjs/web-app`，需 `micro_app=true`：

```js
import { TrimApp } from '@trimjs/web-app';
const sdk = new TrimApp();
await sdk.getPlatformConfig();   // 读系统语言/版本
await sdk.openURL(url);          // 打开外部地址
await sdk.openAppSetting();      // 打开本应用设置页
```

- `sdk.isWeb` / `sdk.isStandaloneWeb` 区分运行环境
- `$on` 监听主题/语言变化**仅在 Web 宿主环境可用**（独立浏览器页面不支持）
- 页面路由：`openFile` / `showFileDetails` / `openFileManager` / `openAppSetting` / `openURL`
  （均需系统 `1.2.0401`、App `1.34.0`）

> **重要**：影视页面本身**不是**微应用环境，注入的 payload **用不了 JS SDK**。
> SDK 只在我们自己的管理页面（`/app/fntvplus/`）里用。

## 三、方案定型：官方合规的「反代注入」

### 3.1 链路

```
用户点桌面图标「影视 Plus」
   │  （官方桌面入口 app/ui/config：type=iframe, url=/app/fntvplus/v/）
   ▼
飞牛统一网关 /app/fntvplus/*  →  fntvplus.sock
   ▼
Go 后端 127.0.0.1:22350
   ├─ 剥离前缀 /app/fntvplus  →  /v/...
   ├─ 回环请求 http://127.0.0.1:$TRIM_SYS_WEB_PORT/v/...（只读，不改任何文件）
   ├─ HTML 响应 → 注入 payload 块 → 返回
   └─ 非 HTML（js/css/图片/视频流）→ 原样透传（含 Range 206）
   ▼
原始影视服务
```

**关键：入口 URL 变了，但这正好用官方桌面入口机制解决**——用户点的是桌面图标，不是手敲 URL。
fndesk 也是这么干的（`url=/app/fndesk`）。

### 3.2 相比「直接改影视 index.html」的收益

| 维度 | 改系统文件 | 反代注入 |
|---|---|---|
| 影视升级失效 | 会，需 watchdog 重注入 | **不会**（每次反代都是最新） |
| 与 fndesk 冲突 | 有（同改 index.html） | **无** |
| 改坏导致影视白屏 | 有 | **无**（只影响自己的入口） |
| 卸载残留 | 需还原备份 | **零残留** |
| 回退方式 | 备份覆盖 | **点原版影视图标即是原版** |
| 合规性 | 改他人应用目录，风险高 | **只读访问，风险显著更低** |

### 3.3 顺带解决 CORS

后端与影视**同源**（都在飞牛域名下）→ payload 调 `/app/fntvplus/api/proxy` 天然无 CORS。
豆瓣、B 站这两个不支持 CORS 的数据源，全部走这个代理。

### 4.3 cmd/main（严格遵循官方退出码）

```bash
#!/bin/bash
BIN="$TRIM_APPDEST/server/fntvplus"
PIDFILE="$TRIM_PKGVAR/fntvplus.pid"
LOG="$TRIM_PKGVAR/fntvplus.log"

start() {
  [ -f "$PIDFILE" ] && kill -0 "$(cat "$PIDFILE")" 2>/dev/null && exit 0
  mkdir -p "$TRIM_PKGVAR"
  nohup "$BIN" --port "$TRIM_SERVICE_PORT" --etc "$TRIM_PKGETC" \
        --var "$TRIM_PKGVAR" --dest "$TRIM_APPDEST" \
        >> "$LOG" 2>&1 &
  echo $! > "$PIDFILE"
  exit 0
}

stop() {
  [ -f "$PIDFILE" ] && kill "$(cat "$PIDFILE")" 2>/dev/null
  rm -f "$PIDFILE"
  exit 0
}

status() {
  # 官方：0=运行中, 3=未运行
  [ -f "$PIDFILE" ] && kill -0 "$(cat "$PIDFILE")" 2>/dev/null && exit 0
  exit 3
}

case "$1" in
  start) start ;; stop) stop ;; status) status ;; *) exit 1 ;;
esac
```

> 失败时用 `echo "原因" > "$TRIM_TEMP_LOGFILE"` 输出用户可见错误，再 `exit 1`。

### 4.4 为什么后端用 Go 而不是 Node

| 维度 | Node | **Go** |
|---|---|---|
| 运行时依赖 | 需探测/下载 node（fndesk 被这问题折磨，最终转 Go） | **单二进制，零依赖** |
| 你已有经验 | — | **有**（`src/modules/proxy` 就是 Go，`build:proxy:*` 脚本现成） |
| 交叉编译 | 需 pkg 打包 | `GOOS=linux GOARCH=amd64/arm64` 一行 |
| 内存占用 | 高 | fndesk 转 Go 后从百 MB 降到十几 MB |

代价：`platform` 需分 `x86` / `arm` 两个包（与 fndesk 一致）。

### 4.5 反代核心（Go，伪代码）

```go
func proxy(w http.ResponseWriter, r *http.Request) {
    // 1) 剥离前缀
    target := strings.TrimPrefix(r.URL.Path, "/app/fntvplus")
    upstream := "http://127.0.0.1:" + webPort + target

    // 2) 转发（透传 Cookie / Range / 自定义头）
    resp, err := transport.RoundTrip(cloneRequest(r, upstream))
    if err != nil { http.Error(w, err.Error(), 502); return }

    ct := resp.Header.Get("Content-Type")

    // 3) 非 HTML：原样透传（含 206 Partial Content）
    if !strings.Contains(ct, "text/html") {
        copyHeaders(w.Header(), resp.Header)
        w.WriteHeader(resp.StatusCode)
        io.Copy(w, resp.Body)
        return
    }

    // 4) HTML：注入 payload
    body, _ := io.ReadAll(resp.Body)
    html := string(body)
    if !strings.Contains(html, "FNTV_PLUS_INJECT_BEGIN") {
        html = strings.Replace(html, "</body>", injectBlock()+"</body>", 1)
    }
    copyHeaders(w.Header(), resp.Header)
    w.Header().Set("Cache-Control", "no-store")   // 防浏览器缓存旧 HTML
    w.Header().Set("Content-Length", strconv.Itoa(len(html)))
    w.Write([]byte(html))
}
```

**必须处理的坑**：

| 坑 | 处理 |
|---|---|
| Range 206（视频流） | 非 HTML 透传时原样保留 `Content-Range` / `Accept-Ranges`；fndesk 的 `index.cgi` 有完整 `dd` 分片实现可参照 |
| WebSocket | 若影视用 WS，需 `Connection: Upgrade` 隧道转发（`golang.org/x/net/websocket` 或 `httputil.ReverseProxy` 已支持） |
| 相对路径 | HTML 内注入 `<base href="/v/">`，或让后端正确处理 `/app/fntvplus/v/**` 任意子路径（推荐后者） |
| 缓存 | 反代响应设 `no-store`；payload URL 带版本号 |
| 压缩 | 若上游返回 gzip，需解压后再注入（或直接删掉 `Accept-Encoding` 请求头） |

### 5.2 Host 适配层

```ts
export interface Host {
  isElectron: boolean;
  storage: { get(k: string): Promise<any>; set(k: string, v: any): Promise<void> };
  request(opts: { url: string; method?: string; body?: any }): Promise<any>;
  log(...args: unknown[]): void;
}
```

- Electron 端：`storage` → IPC 写配置文件；`request` → 主进程 axios（可自定义代理/TMDB IP）
- 浏览器端：`storage` → localStorage；`request` → `fetch('/app/fntvplus/api/proxy', ...)`

### 5.3 构建

新增 `scripts/build-userjs.js`（esbuild）：

```bash
npm run build:userjs   →  dist/fntv-plus.user.js（IIFE 单文件）
```

产物同时用于：① FPK 的 `app/server/payload/` ② 本地 Playwright 回归。

### 5.4 客户端去重

`preload/core/remoteGuard.ts`：检测到 `window.__FNTV_PLUS__` 已存在 → 跳过本地同 id 插件。

客户端 `loadURL` 目标可配置为 `/app/fntvplus/v/`（增强版）或原 `/v`（原版），由用户选。

### 5.5 已落地的复用机制（实际做法，替代 5.1 的 web/host 拆分）

经实测，Fntv-Plus 现有 preload **并未**按 web/host 拆分；且 `embyWall.ts` 在被 `import` 时通过
`registerHook(HookType.OnReady, handle)` 自注册。因此采用**零改写复用**：

1. 将 `Fntv-Plus/src/preload`（含 `plugins/embyWall`、`core/*`）**逐字复制**到本项目的 `src/preload/`。
2. `src/web-entry.ts` 只做两件事：`import './preload/plugins/embyWall'`（触发自注册）+ DOM ready 后 `runHooks(OnReady)`。
3. `src/shim/electron.js` 提供浏览器版 `ipcRenderer`/`shell` 垫片（`settings:*` 走 localStorage，其余 no-op），
   由 esbuild `alias: { electron: shim }` 注入；`process.env.NODE_ENV` 用 `define` 处理。
4. `scripts/build-userjs.mjs`（esbuild）打包为 `dist/fntv-plus.user.js`（IIFE，约 770KB）。
5. `scripts/serve.mjs` 本地静态服务 + `demo/host.html` + `scripts/smoke.mjs`（Playwright 冒烟）用于回归。

> 注意：`animeLib/customLogo/titlebar` 用到 `fs/path`，但它们**不在** `embyWall` 的导入图里，打包器不会纳入；
> 真正进入包体的只有 embyWall 及其依赖（轮播、沉浸式美化、玻璃、Logo 等）。
> 该 `user.js` 即 FPK 反代要注入到影视页面的 payload，已通过冒烟测试（boot 就绪、样式注入、零报错）。

## 七、目标群体定位与「外部播放器」硬边界

### 7.1 目标群体（用户需求锁定）

> **不想在电脑上安装任何客户端，希望「NAS 上装一个应用就完事」的人。**

这个定位是**正确且关键**的产品决策，它直接决定了方案的取舍边界。

### 7.2 硬边界：NAS 上的程序够不着用户电脑上的播放器

参照项目 `embyToLocalPlayer`（已克隆至 `D:\GitHub\Fntv-Plus-Desktop\embyToLocalPlayer`）实证：

| 环节 | 实现位置 |
|---|---|
| 网页 → 发「请播放」指令 | 油猴脚本 `GM_xmlhttpRequest` → `http://127.0.0.1:58000`（需 `@connect 127.0.0.1` 权限绕过 mixed content） |
| 拉起播放器 | **本机 Python 服务**（`utils/http_server.py` 监听 58000） |
| **回传进度到服务器** | **本机 Python 服务**（`player_manager.py` / `emby_api.py`） |

**结论**：embyToLocalPlayer 的「回传进度」是**本机常驻服务**做的，网页只发了一条单向指令。
它要求用户：装油猴插件 → 下载 zip 解压 → 双击 bat → 设开机自启（README 原文）。
**它比装一个 Fntv-Plus 客户端还麻烦** —— 与本项目的目标群体直接冲突。

**根本矛盾**：FPK 跑在 NAS 上，MPV 在用户电脑上，中间隔着网络。
**想用 MPV，就必须在本机常驻一个服务**；而目标群体恰恰不想在本机装任何东西。
→ **对这群人，MPV / PotPlayer / 着色器 / 硬解 全部无解，不是技术问题，是物理隔离。**

### 7.3 重定位：这群人真正需要什么

他们本来就是**用浏览器原生播放器看片**的人，痛点在「看的体验」，不在「用哪个播放器」：

| 真实痛点 | 我们的解法 | 可行性 |
|---|---|---|
| 原生网页播放器没弹幕 | `danmakuWeb`（canvas 叠加，已现成） | ✅ |
| 没有跳过片头片尾 | 改 `skipInject` 直接操作 `video.currentTime` | ✅ |
| 自动连播弱 | `autoplayNext`（监听 `timeupdate`） | ✅ |
| 字幕体验差（外挂/样式/匹配） | 字幕轨道自动选择 + 样式自定义 | ⚠️ 需 hook |
| 高码率/HEVC 卡顿 | **FPK 后端转码策略优化**（见下） | ✅ |
| 原生影视 UI 一般 | UI 增强（详情页/轮播/玻璃/Logo） | ✅ |
| 平板 / 手机访问 | 响应式与触摸优化 | ✅ |
| 进度不同步 | 网页端监听 `video` 回传飞牛（同源 API） | ✅ **比客户端更简单** |

### 7.4 【补充场景】NAS 性能不足、必须本地硬解的用户

> 典型诉求：NAS 转码能力弱，4K / HEVC / 高码率原盘浏览器播不动，需要本机 MPV / PotPlayer 硬解，
> 并且希望进度能回传飞牛。

**结论：这个需求真实且重要，但纯 NAS 端 FPK 无法满足 —— 有三重硬障碍，均为物理/协议层面，非工程量问题。**

| # | 障碍 | 证据 |
|---|---|---|
| 1 | **网页调不起本机播放器** | FPK 在 NAS，MPV 在用户电脑，中间隔着网络 |
| 2 | **复制直链给 MPV 也不行** | 飞牛直链 `/v/api/v1/media/range/{guid}` **需 Authx/cookie 鉴权，直接给 MPV 会 403**<br>（本项目已踩坑：`embyWall/nav/inject.ts:161` lc-595；正确做法是提取 guid 后经 **Go 代理注入 cookie** 播放） |
| 3 | **进度回传需要本地进程** | 需持续监控播放器状态再调 `POST /v/api/v1/play/record`；浏览器里的 JS 无法感知本机播放器 |

**即：外部播放 = 本机必须有进程（代理注入鉴权 + 监控播放器）。零安装无解。**

#### 正确做法：产品矩阵分流，而不是硬塞进 FPK

| 用户群 | 特征 | 方案 | 说明 |
|---|---|---|---|
| **A 轻量** | NAS 够用 / 主要看低码率 / 不想装东西 | **FPK 网页端增强** | 本方案主目标 |
| **B 重度** | NAS 弱、要看 4K 原盘、必须本地硬解 + 回传 | **Fntv-Plus 客户端** | **已有完整能力**，且这群人装客户端动机最强 |
| C 中间 | 偶尔卡 | FPK + 智能降级 | 见下 |

> **B 群不需要新方案** —— Fntv-Plus 客户端已经把「调起 MPV/PotPlayer + 鉴权代理 + 进度回传 + 弹幕 + 跳过」全做完了。
> 且这群人的核心痛点（NAS 弱）决定了他们有强动机装客户端，不属于「嫌麻烦」人群。

#### FPK 侧能做的补偿（把 B 群用户导流到客户端）

1. **智能检测 + 引导**（最高性价比）
   - 检测视频编码/码率 + 浏览器解码能力（`video.canPlayType()` / `MediaCapabilities`）
   - 判定「浏览器可能播不动」→ 播放页提示：**「此片建议本地硬解，用 Fntv-Plus 客户端更流畅」** + 下载链接
   - 这既帮了用户，又给客户端导流，形成漏斗而非冲突
2. **硬件转码检测与引导**
   - 检测 NAS 是否支持 QSV / VAAPI / NVENC，引导用户在影视设置里开启硬件转码
   - 开启后多数中高码率场景网页端即可播放
3. **预转码缓存**（可选，M5 之后）
   - 对频繁播放的高码率片源，低峰期后台转低码率版本缓存，播放时直取
   - 需设空间上限与清理策略
4. **高级用户出口**：生成带鉴权的播放命令（如 `mpv --http-header-fields="Authx: ..." "<url>"`）供手动复制
   —— 仅面向极客，不做为主路径

### 7.5 fntv:// 单向唤起（能调起即可，进度回传搁置）

> **决策**（用户 2026-09-07）：外部播放器「先做个能调起就行，其余关键回传先搁置」。
> 把 `fntv://` 从评估文档 4.1 节的「P3、可不做」提升为 **M4 阶段实际交付项**，但只做**单向遥控器**形态，
> 不承诺「网页端看到实时播放状态」（评估文档 4.1 节第 5 步，本就是搁置项）。

**形态（只做这一件事）**：

```
网页 payload：用户手势内点「用本机播放器打开」
  → 构造 fntv://play?guid=<guid>
  → 浏览器唤起已安装的 Fntv-Plus 客户端
  → 客户端自调飞牛 API 补全信息 → spawn MPV / PotPlayer
  → 页面 toast「已发送到 Fntv-Plus」
  → 3s 内页面未失焦 → 提示「未检测到客户端，点此下载」
```

**为什么够用**：

- 客户端被唤起后，spawn MPV + **进度回传飞牛** 是客户端进程内全能力，照常工作；
  「丢的」只是网页端看不到实时状态——正是「先搁置」的部分。
- URL **绝不带 token**：协议参数会落浏览器历史 / 系统日志 / 第三方可见；
  token 由客户端 `handlePlayMovie` 的 [lc-596] 兜底从 config 读取。

**依赖（客户端侧）**：客户端需注册 `fntv://` 协议。参考实现已沉淀在
`D:\GitHub\Fntv-Plus-Desktop\lc-1105-fntv-protocol.patch`
（从 Fntv-Plus 导出，含 `protocolHandler.ts` + `media.ts` 的 `playMovieByGuid` + `main.ts` 接线 + 三平台 `package.json` 协议声明）。
**该 patch 暂未合入 Fntv-Plus**——用户要求代码改动只在新项目工作目录进行；待授权后，
将 `protocolHandler.ts` 移植进客户端侧代码，payload 侧按钮即可生效。

**网页侧（本 FPK 项目交付物）**：在 payload 播放控制条加一个按钮，点击在用户手势内执行
`location.href = 'fntv://play?guid=' + guid`；用 `blur` / `visibilitychange` 在 3s 内判断页面是否失焦，
未失焦则弹「未检测到客户端」提示 + 下载链接。纯 DOM，无需 NAS 后端改动。

**已知边界（记入风险，不解决）**：

- 可靠性约 55%（评估文档 4.1 节）：首次弹确认框、未注册时静默失败、绿色版 / 移动目录致协议失效。
- 进度状态回传网页端：搁置（https 页调 http 本地端口还会被 mixed content 拦，物理上不可行）。

### 7.6 FPK 后端能做而客户端做不到的事（新增价值）

1. **转码策略优化**：影视本身有转码能力；后端可按客户端 UA/带宽推荐码率，或在卡顿时自动降档。
2. **字幕预处理**：字体子集化、编码统一（GBK→UTF-8）、时间轴校准。
3. **媒体信息预取与缓存**：详情页秒开。
4. **同局域网多端共享配置**：配置存在 NAS 上，换设备/换浏览器都跟着走（客户端是本机存储，做不到）。

> 第 4 点是个真正的差异化：**客户端的配置存在用户电脑上，网页端的配置存在 NAS 上，
> 对「多设备看片」的人是实打实的体验提升。**

## 十、风险与合规（必须知道）

1. **注入影视页面属灰色地带**：官方文档**没有**提供「修改其他应用页面」的能力。
   我们的做法是「只读回环 + 响应注入」，不改影视任何文件，风险显著低于 fndesk 的直接改写，
   但仍依赖影视页面的 DOM/结构，**影视大版本升级可能导致 payload 失效**（不会导致影视不可用，最坏情况是增强不生效）。
2. **同源代理 = 新攻击面**：`/api/proxy` 必须 **域名白名单 + HMAC 签名 + 禁止内网/回环地址**，
   否则等于给 NAS 开公开代理（fndesk 就因安全问题做过加固）。
3. **`TRIM_API_TOKEN` 严禁持久化/下发前端**，每次从环境变量读。
4. **回环读影视需要 root**，属必要权限，在 `config/privilege` 声明并告知用户。
5. **DOM 漂移**：与客户端现状同量级（同一份页面 DOM），建议 payload 内加「DOM 断言 + 失败静默降级」。
6. **飞牛 App / TV 端不生效**（原生渲染，不加载 `/v` 网页），能力边界要写清楚。
7. **测试机原则**：官方明确建议用专门测试设备，别拿存重要数据的机器反复装卸。
8. **`fntv://` 单向唤起（M4）的可靠性边界**：仅做「能调起」，不承诺网页端看到播放状态。
   已知可靠性约 55%（首次弹确认框、未注册协议时静默失败、绿色版/移动目录致协议失效）；
   「进度回传网页端」物理上不可行（https 页调 http 本地端口被 mixed content 拦），**明确搁置，不向用户承诺**。
   客户端侧 `fntv://` 处理器（`lc-1105-fntv-protocol.patch`）暂未合入 Fntv-Plus，按钮生效以客户端合入为前提。
